# アーベル 入退室システム 設計メモ

- 作成日：2026-11-08
- 状態：検討中（本メモは決定事項と未確認事項を分けて記録する）
- 対象：学生コミュニティスペース「アーベル」（無料・24時間／要予約、連絡は公式LINEに集約）

---

## 1. 課題

- 入退室システムは既にあるが、利用者が毎回操作してくれない。
- 主なパターンは「登録はしているが、毎回は押さない」。
- 入口QR／POP、利用理由の説明、特典導線、声かけ等の基本的な促進策は実施済み。
  → 周知・呼びかけの問題ではなく、「任意の自己申告に任せる」仕組み自体が限界という前提で設計する。

## 2. 方針（結論）

無人コワーキングで一般的な「3型」をアーベル用に読み替える。

> **読み取り ＝ 解錠 ＝ 入室記録** とする。課金連動は行わない。

- チェックインという独立した任意操作をなくし、ドアを開ける行為そのものを記録にする。
- 鍵の開閉は設置済みの SwitchBot をそのまま使う。新規の業務用ロック（RemoteLOCK等）への置き換えはしない。
- 本人確認はスマホ1台＝LINEアカウントで行う。専用アプリの追加インストールは求めない。

## 3. 希望導線（中上の指定）

```text
公式LINEを友だち追加
  → 会員登録（LINE内で完結）
  → 以後はスマホ1台で、登録済み会員だけが解錠して入室できる
```

- システムの仕様書も作成し、GitHub で管理して、そのURLを公式LINEで公開する予定。
- 会員システムと LINEアカウントの紐付けを仕様に含める。
- 確認通知の通数対策 (2026-11-08): プッシュは通数課金の対象だが、応答メッセージ (Reply API) とLINEチャット・あいさつメッセージは対象外 (LINE公式ヘルプ)。確認系はLIFF画面表示＋Replyで返して通数を消費せず、12時間自動退室のような能動通知は原則プッシュせず画面表示で代替する方針を仕様書 §8-1 に明記。

## 4. 利用者の流れ

### 4-1. 初回登録（1回だけ）

1. 公式LINE（https://lin.ee/RbF8i6j ）を友だち追加する。
2. リッチメニュー等から「会員登録」を開く（LINE内Web画面＝LIFF）。
3. 必要項目を入力して登録する（登録項目は §8 の確認事項）。
4. 登録と同時に、その人の LINEユーザーID と会員レコードを紐付ける。
5. 登録完了メッセージをLINEで返す。以後は解錠可能になる。

### 4-2. 入室（毎回）

1. 入口のQRコード（印刷）またはNFCタグをスマホで読む。
2. LINE内画面が開き、サーバーが「このLINEユーザーIDは有効な会員か」を照合する。
3. 会員であればサーバーが SwitchBot に解錠信号を送り、同時に「誰が・いつ」入室したかをログに記録する。
4. 会員でなければ解錠せず、登録フォームへ誘導する。

※ 入口QR自体は秘密情報ではない。写真で共有されても、読み取った本人のLINEが会員でなければ開かない。

### 4-3. 退室（決定・2026-11-08）

- 退室も記録を取る（退室ボタン／室内QR）。ドア自体は内側から通常どおり開けて出られ、施錠は SwitchBot のオートロックに任せる。
- **退室が取れていない場合は、入室から12時間で自動退室扱いにする。** 滞在時間は一律720分として記録し、実際の退室と区別する（仕様書 §14-2）。

### 4-4. 利用停止・退会

- 管理者が会員レコードのステータスを「停止」に変えるだけで、次回から解錠できなくなる。
- 鍵番号の変更、カード回収等は不要。

### 4-5. ゲスト・一時利用

- 原則は会員のみ。イベント時等のゲスト対応は、運営が SwitchBot アプリから遠隔解錠する運用でカバーする（MVP）。
- 恒常的に必要になったら、期限付きのワンタイム解錠リンク／暗証番号を Phase 3 で検討する。

## 5. 仕組みの要点

| 要素 | 方式 |
|---|---|
| 本人確認 | LINEユーザーID（LIFFのIDトークンをサーバー側で検証して取得。画面表示の名前等は信用しない） |
| 会員との紐付け | 新規登録時はLIFFで取得したLINEユーザーIDを会員レコードに保存。既存の会員IDがある場合は公式の「アカウント連携」（連携トークン＋nonce＋Webhook）で紐付ける（詳細は仕様書 §4） |
| 解錠 | サーバー → SwitchBot API（unlockコマンド）→ ハブ経由でロック解錠。トークン類はサーバー側のみに置き、利用者の画面からは直接解錠させない |
| 入口の読み取り | 利用者のスマホが読み取り機になる（固定QR／NFCタグ）。読み取り専用機は買わない |
| 記録 | 解錠リクエストの成否をすべてログ化する（成功＝入室記録、失敗＝未登録・停止等の理由付き） |

## 6. 費用（最安構成）

| 項目 | 金額 | 備考 |
|---|---|---|
| 入口QR（印刷・ラミネート） | ほぼ0円 | NFCタグにする場合も1枚数百円程度 |
| SwitchBotロック | 0円（設置済み） | 既存を流用 |
| ハブ | 0円〜5,480円 | ハブが既にあるか未確認。無い場合はハブ2（9,980円）でなくハブミニ（公式5,480円・税込）で足りる |
| サーバー／連携ソフト | 0円想定 | Google Apps Script 等の無料範囲で構築する想定。無料枠の上限は実装時に確認 |
| LINE公式アカウント／LIFF | 追加開発費なし | 既存アカウントを使用。配信数が増えた場合のプラン料金は別途確認 |
| 月額 | **0円** | SwitchBot側の月額課金なし |

比較のため調査した代替案（採用しない）：
- KEYVOX QR1 LE（読み取り機 50,600円）：連携先がセサミ／PiACKII／電気錠等で、SwitchBotとは直結しない。
- RemoteLOCK 9j-Q（本体207,900円、導入総額 約26〜36万円＋月2,200円）：業務用一体型。既にSwitchBotがある現状では過剰。

## 7. リスクと予備手段

| リスク | 対策 |
|---|---|
| スマホの電池切れ・紛失で入れない | 運営が SwitchBot アプリから遠隔解錠できる体制を維持。物理鍵の保管場所と管理者を決めておく（保管場所は公開仕様書には書かない） |
| ハブ／Wi-Fi／ネット障害で解錠信号が届かない | 障害時の連絡手段（公式LINE）と遠隔・現地対応の手順を運用メモに残す |
| 共連れ（1人の解錠で複数人が入る） | 仕組みでは防げない。規約で禁止し、必要なら記録との突合で対応する。本メモでは過剰な対策は入れない |
| QRのなりすまし・連打 | 解錠判定は毎回サーバー側で会員照合する。短時間の連続解錠にはクールダウン（例：30秒）を設ける |
| GitHub公開による情報漏えい | 公開仕様書には秘密情報を書かない（§9）。認証情報・デバイスID・物理鍵の場所・迂回手順は非公開の運用メモに分離する |

## 8. 未確認事項（実装前に決めること）

1. **SwitchBotのハブの有無**（ハブミニ／ハブ2／ハブ3 のいずれかがあるか）。解錠信号の経路が決まる最重要項目。
2. 現在の入退室システムの基盤（自作か外部サービスか、会員データはどこにあるか）。移行か連携かで作業が変わる。
3. 会員登録の入力項目（氏名のほか、大学・学年・連絡先など何を取るか）。
4. 既存の会員ID／会員データがある場合、アカウント連携で移行するか、新規登録し直してもらうか。
5. ~~退室時刻の記録が必須かどうか~~ → **決定済み（2026-11-08）：退室も取る。取れていない場合は12時間で自動退室扱い（ §4-3）。**
6. 予約との連動をいつ入れるか（MVPは会員チェックのみ、予約時間帯チェックは Phase 3 を想定）。
7. GitHubのリポジトリ名・アカウントと、公開範囲（Public前提。ただし §9 の分離を守る）。
8. ~~利用時間ランキングのための退室時刻の取り方~~ → **決定済み（2026-11-08）：退室記録があればそれを使い、無ければ入室から12時間で自動退室扱い。**
9. ランキングを会員にも見せるか（見せる場合は表示名と同意の扱い）。

## 9. 成果物と公開の進め方

1. 本設計メモ（内部用：判断の経緯・費用・未確認事項）。
2. システム仕様書（`spec.md`）：GitHubリポジトリで管理する前提で作成済み。
   - 公開版：導線、機能、画面、データ項目、APIの考え方、LINEアカウント連携の手順。
   - 非公開（リポジトリに入れない）：SwitchBotトークン／LINEチャネルシークレット等の認証情報、デバイスID、物理鍵の保管、障害時の迂回手順。
3. GitHub の URL ができたら、公式LINEのリッチメニューと配信で公開する。

## 10. 実装フェーズ

- **Phase 1（MVP）**：LINE追加→登録→LINEユーザーID照合→SwitchBot解錠→入室ログ＋退室記録（取れていない場合は12時間で自動退室）。管理者画面の最小版（会員一覧・ステータス変更・本日の入室数）と、利用回数・利用時間ランキングはこの段階でも出せる。
- **Phase 2**：管理者画面の本格版（ダッシュボード、利用歴検索、利用歴のCSV書き出し）、月次の利用集計（延べ人数・実人数）の出力＝協賛報告に使える形。
- **Phase 3**：予約データとの連動（予約時間帯のみ解錠可）、ゲスト用ワンタイム解錠。
